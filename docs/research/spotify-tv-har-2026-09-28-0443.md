## Conclusion

This recording closes several gaps in the [first capture](spotify-tv-har-2026-09-27.md):
Spotify's TV client can read Explore/browse data and can save and unsave
metadata entities through the private TV GraphQL endpoint. The recorded Search
request returned an empty JSON object, so it does not validate search results.
There was no token-refresh request. The TV bundle establishes refresh request
construction separately; see the [refresh analysis](spotify-tv-refresh-and-followup.md).

These are account metadata operations. The capture does not validate Spotify
audio playback or require a MusicViz playback change.

Two `fetchPlayerOptions` calls also succeeded; they serve Spotify player
behavior and are outside the metadata plugin's first phase.

The `curateItem` requests target a track and a playlist. The `uncurateItem`
request targets a track. Each readable mutation response includes a `responses`
list with context and entity fields; HTTP 200 alone is not a sufficient
confirmation of a successful user-facing save. Parse the operation response,
then reconcile the local saved state. Playlist unsaving and artist following
are not validated by this capture.

`browseAll` returns a `browseStart` section container. The inspected
`browsePageTraits` response has a header title and eleven sections, including
section items and paging metadata. The plugin should translate these provider
DTOs into the SDK's typed page blocks, filters and category targets. Do not make
MusicViz render Spotify's raw GraphQL wrapper types.

## Search limitation

The `search` request reached curiosity and returned HTTP 200. Its recorded
response body is exactly `{}` (two bytes); therefore it establishes a request
name and variable names but no results, type tabs, suggestions, or paging.
Wiretrail redacted the whole-object extract for this entry. A bounded inspection
of that single HAR response confirmed the two-byte body without printing the
query or account data.

This may be a preparatory request rather than the operation supplying the
visible results. That is an inference. The TV bundle contains separate search
operations, but their execution and response shapes still need a targeted live
capture or explicit authorized test. A full SDK provider cannot claim its
required artist, album and playlist Search contract is validated by `e000042`.

## Refresh boundary

No `accounts.spotify.com/api/token` call is present in this HAR. The local
Spotube reference renews a web-player token from `sp_dc` and TOTP; that flow
does not apply to the TV device-code session. The public TV JavaScript sends
`grant_type=refresh_token`, the current refresh token and TV client ID to
`accounts.spotify.com/api/token`, and stores a replacement refresh token when
one is returned. This is source-code evidence for request construction, not
a captured refresh response or live test. See the refresh analysis for the
SDK's session and concurrency requirements.
